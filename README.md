# TaskFlow

Трекер задач для команди: робочі простори, проєкти, Kanban-дошка з drag & drop,
коментарі, історія змін і оновлення в реальному часі.

Бекенд — NestJS + PostgreSQL + Prisma, фронтенд — React + TypeScript (Vite).
Автентифікація на JWT, realtime через socket.io, черга email на Redis.

## Запуск

Потрібен Docker.

```bash
cp .env.example .env
docker compose up --build
```

Підніметься 5 контейнерів: postgres, redis, mailhog, backend і frontend.
Міграції застосовуються автоматично. Далі — http://localhost:3000, реєструйся і працюй.

Корисні адреси:

- http://localhost:3000 — застосунок
- http://localhost:8080/api/docs — Swagger
- http://localhost:8080/api/health — health-check
- http://localhost:8025 — Mailhog, тут видно листи із запрошеннями

### Без Docker

Треба Node.js 20+, PostgreSQL і (за бажанням) Redis.

```bash
cd backend
cp ../.env.example .env       # у DATABASE_URL заміни host postgres на localhost
npm install
npx prisma migrate deploy
npm run prisma:seed           # демо-дані, необов'язково
npm run start:dev
```

```bash
cd frontend
npm install
npm run dev
```

Після сіду можна зайти як `owner@taskflow.local` / `Password123`.
Без Redis теж працює — якщо черга недоступна, лист відправляється синхронно.

## Чому такий стек

**PostgreSQL.** Дані тут сильно зв'язані: користувач → простір → проєкт → задача →
коментар, плюс історія змін і виконавці. Реляційна база дає цілісність через зовнішні
ключі, каскадні видалення й нормальні індекси під фільтри. З документною довелося б
збирати зв'язки руками.

**Prisma.** Схема в одному файлі, звідти генерується типізований клієнт і міграції.
Індекси описуються декларативно.

**Фронтенд.** TanStack Query для серверного стану — його кеш зручно патчити з
WebSocket і робити оптимістичні оновлення. Zustand для сесії, react-hook-form + zod
для форм, @dnd-kit для перетягування, Tailwind для верстки.

## Як влаштовано

### Бекенд

```
src/
  config/       валідація змінних оточення (zod)
  prisma/       підключення до бази
  persistence/  усі репозиторії
  common/       обробка помилок, метрики, пагінація, перевірка прав
  auth/         реєстрація, вхід, вихід, оновлення токенів
  users/        профіль і пошук за email
  workspaces/   простори, ролі, учасники, запрошення
  projects/     проєкти
  tasks/        задачі, коментарі, історія змін
  realtime/     WebSocket-шлюз
  queue/ mail/  черга та відправка листів
  health/       health-check
```

Ланцюжок такий: контролер → сервіс → репозиторій → Prisma. Про ORM знає тільки
репозиторій, тому сервіси легко покривати тестами з простими моками. Репозиторії
винесені в глобальний `PersistenceModule`, щоб не було циклічних залежностей.

Назовні нічого не віддається «сирим» — усе через DTO. Права перевіряються в одному
місці (`AccessControlService`), звідти ж послідовні коди: 404 якщо сутності немає,
403 якщо немає доступу, 409 на дублікати. Глобально висять guard автентифікації,
rate limiter, фільтр помилок і інтерсептор, який пише час відповіді.

### Фронтенд

Структура за Feature-Sliced Design:

```
src/
  app/       провайдери, роутер, стилі
  pages/     сторінки
  widgets/   складені блоки (дошка, деталі задачі, шапка)
  features/  дії користувача (логін, керування задачами, фільтри, коментарі)
  entities/  сутності (user, session, workspace, project, task, comment)
  shared/    ui-кіт, http-клієнт, конфіг, утиліти
```

Кожен слайс має `index.ts` — імпортувати можна тільки через нього. Шари залежать
строго вниз: `app → pages → widgets → features → entities → shared`. Сусіди по шару
одне одного не імпортують: `entities/session` бере тип користувача через
`entities/user/@x/session`. Усі три правила перевіряє ESLint, тому це не домовленість
на словах, а помилка збірки.

Дошка оновлюється з WebSocket — події точково правлять кеш React Query, без повного
перезапиту. Перетягування працює оптимістично: картка стрибає одразу, при помилці
кеш відкочується.

## Модель даних

`User`, `RefreshToken`, `Workspace`, `WorkspaceMember` (роль OWNER або MEMBER),
`Invitation`, `Project`, `Task`, `Comment`, `TaskActivity`.

Індекси стоять там, де реально фільтруємо: `Task` по `(projectId, status, position)`,
окремо по `assigneeId` і `priority`, `email` у `User`. Схема — `backend/prisma/schema.prisma`.

## Безпека

Токени лежать у httpOnly-cookie, а не в localStorage. Сенс у тому, що JavaScript
не має до них доступу, тож навіть якщо десь пролізе XSS, вкрасти токен не вийде.
Access живе 15 хвилин, refresh — 7 днів і обмежений шляхом `/api/auth`, щоб не
їздити з кожним запитом. Обидві cookie з `SameSite=Lax`, у продакшені ще й `Secure`.
У тілі відповіді на логін токенів немає взагалі — тільки профіль. WebSocket
автентифікується тією ж cookie.

Refresh-токени ротуються: у базі зберігається лише SHA-256 хеш, при оновленні старий
відкликається. Якщо хтось спробує використати вже відкликаний токен, відкликаються
всі токени користувача — це ознака крадіжки.

Решта: паролі через bcrypt, глобальна валідація з відкиданням зайвих полів,
rate limiting (суворіший на логіні), Helmet, CORS за списком. SQL-ін'єкції закриті
параметризованими запитами Prisma, XSS — валідацією на вході й екрануванням React.

## Тести

```bash
cd backend && npm test          # unit
cd backend && npm run test:e2e  # потрібна запущена PostgreSQL
cd frontend && npm test
```

Unit — `tasks.service` (історія змін, права, пагінація, edge-кейси).
E2E — реєстрація → простір → проєкт → задача → переміщення → історія, плюс cookie,
ротація токенів і перевірки доступу. На фронтенді — `TaskCard` і утиліти дошки.

CI (GitHub Actions) на кожен push ганяє лінт, тести й білд для обох частин.

## API

Swagger — http://localhost:8080/api/docs.
Схему можна вивантажити файлом: `cd backend && npm run openapi:export` →
`backend/openapi.json`, імпортується в Postman.

## Що спростив

- Порядок задач у колонці — звичайний цілочисельний `position` без переіндексації
  сусідів. Для продакшену взяв би lexo-ранги й атомарний reorder.
- Дошка тягне до 100 задач одним запитом і групує їх на клієнті. Серверні фільтри
  й пагінація при цьому реалізовані повністю.
- CSRF закритий тільки через `SameSite`. Якщо фронтенд буде на іншому домені,
  треба додати CSRF-токен.
- Тести показують підхід, а не покривають усе.
- Ролі спрощені до OWNER/MEMBER, окремого шару політик немає.
- Репозиторії віддають типи Prisma. Щоб повністю відв'язатися від ORM, потрібні
  доменні моделі й мапери — для такого обсягу це зайве.
